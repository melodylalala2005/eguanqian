# 技术架构

鹅管钱是前后端分离的全栈应用：iOS 客户端负责本地数据与交互，Python 后端负责账单图片识别与数据持久化。

```
┌──────────────────────────────────────────────────────────────┐
│                        iOS 客户端 (SwiftUI)                   │
│                                                              │
│  Views ──► ViewModels ──► Services(协议) ──► ┌─────────────┐ │
│                                              │ SwiftData   │ │
│  识图记账 ──────────► ReceiptRecognition ────┤ (本地账本)  │ │
│  账单同步 ──────────► BillSyncService  ──────└─────────────┘ │
└──────────────────────┬───────────────────────────────────────┘
                       │ HTTP (multipart / JSON)
┌──────────────────────▼───────────────────────────────────────┐
│                    后端 (FastAPI + Uvicorn)                   │
│                                                              │
│  /upload_baidu_qwen  百度 OCR + Qwen 文本模型 (默认)          │
│  /upload_qwen_vl     Qwen-VL 多模态直接识图                   │
│  /upload_llm         自然语言文本解析                         │
│                                                              │
│  Token 鉴权 ──► SQLite (bills / users)                       │
└──────────────────────────────────────────────────────────────┘
```

## iOS 客户端

- **语言/UI**：Swift + SwiftUI，最低部署目标 iOS 17
- **本地存储**：SwiftData（`@Model` 实体：`Transaction`、`TransactionCategory`、`BudgetPlan`、`FinancialAssetEntity` 等）
- **架构**：MVVM + 依赖注入。`FinanceEnvironment` 是组合根，持有所有服务的协议引用，便于在 Mock 与网络实现之间切换
- **网络层**：`FinanceAPIClient` 封装泛型 `APIRequest`，`Networking.swift` 定义 `BillSyncService` 与 `APIConfiguration`

### 服务协议（可插拔）

| 协议 | 网络实现 | Mock 实现 | 职责 |
| --- | --- | --- | --- |
| `TransactionRepository` | — | ✅ | 交易增删改查、分段时间切片 |
| `BudgetService` | — | ✅ | 预算计划、分类预算、已用额度 |
| `StatisticsService` | — | ✅ | 月度/年度快照、类别汇总、目标对比 |
| `AIChatService` | — | ✅ | AI 理财助手对话 |
| `BillSyncService` | `NetworkBillSyncService` | — | 交易同步到后端 `/manual_bill` |
| `ReceiptRecognitionService` | `NetworkReceiptRecognitionService` | — | 调用后端 `/upload_baidu_qwen` 识图 |

> Mock 实现让前端可以在无后端的情况下独立开发和预览。

### 识图记账流程

1. `ReceiptCameraCaptureView` 拍摄/选取账单图片
2. `ReceiptImagePreprocessor` 预处理图片
3. `ReceiptRecognitionQueueStore` 入队，`ReceiptRecognitionCoordinator` 调用后端
4. 后端返回结构化结果 `{category, amount, date, description, nw_type}`
5. 写入 SwiftData 并通过 `BillSyncService` 同步到云端
6. `RecognizedReceiptHistoryStore` 保留识别历史

### 分类体系

`CategoryDefinitions` 定义了 13 个支出类别 + 4 个收入类别，每个类别带 emoji 与品牌色；另有「基础支出/娱乐支出」二级 `SpendingType` 分类，与后端 `nw_type` 字段对应。

## 后端

- **框架**：FastAPI + Uvicorn（ASGI）
- **存储**：SQLite3（Python 标准库，零安装）
- **鉴权**：注册/登录返回 30 天有效期的 token（`secrets.token_urlsafe(32)`），密码 SHA-256 加盐
- **LLM 网关**：通过 OpenAI SDK 兼容协议调用 DashScope

### 三条解析链路

| 端点 | 模块 | 引擎 | 输入 |
| --- | --- | --- | --- |
| `/upload_baidu_qwen` | `services/baidu_qwen.py` | 百度 OCR + Qwen 文本模型 | 图片 |
| `/upload_qwen_vl` | `services/qwen.py` | Qwen-VL 多模态 | 图片 |
| `/upload_llm` | `services/llm.py` | Qwen3-VL（OpenAI 兼容） | 文本 |

三者共用一套提示词与返回结构，返回统一 JSON：

```json
{
  "category": "餐饮",
  "amount": "38.50",
  "date": "2025-11-16",
  "description": "食堂午餐",
  "nw_type": "基础支出"
}
```

### API 一览

| 方法 | 路径 | 鉴权 | 说明 |

完整字段说明见 [`server/README.md`](../server/README.md)。

## 关于方案与实现的说明

产品文档（`docs/市场与产品文档/04-技术与评估.md`）描述的评估对象是 **PaddleOCR + Qwen2.5-Turbo** 的选型验证；仓库内的后端实现落地的则是 **百度 OCR + Qwen** 与 **Qwen-VL** 两条链路（通过 DashScope 兼容协议调用）。两者是「方案验证」与「工程实现」的关系——评估证明了 OCR+LLM 路线的可行性，实现则选用了当时云端可直接调用的等价服务。如需复现文档中的方案，可在 `services/` 下按同一接口新增 PaddleOCR 适配。
